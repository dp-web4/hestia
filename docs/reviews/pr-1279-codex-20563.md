## P1: equality still silently permits source-build and prerelease downgrades

In `deploy/fleet/install.sh:882-892`, `guard_downgrade` extracts only the installed
numeric triple, strips the target suffix, and accepts equality. The CLI's
`VERSION` in `core/src/cli.rs` includes build provenance, but the guard discards it.
Thus `hestia 0.0.4 (v0.0.4-12-gabc1234)` can be replaced by `v0.0.4` without
the operator's downgrade override. Reproduced through all three selection paths:
explicit pin, API latest, and API-failure fallback. The fallback announces API
failure, but none of these paths announces the source-code downgrade or refuses it.

Likewise, a genuine stable `hestia 0.0.4 (v0.0.4)` silently passes for target
`v0.0.4-rc.1`. Stripping everything after the first hyphen also means the claimed
non-X.Y.Z refusal does not apply to targets such as `v0.0.4-not-a-release`.
These paths return success before the new comparator runs, so improving that
comparator cannot close this finding.

Preserve build provenance and release/prerelease ordering before accepting
equality. Require an affirmative override for known downgrades, and refuse with
an explanation when the relationship cannot be established. Preserve a genuine
same-release reinstall. Use genuine release output for the existing idempotence
test: its current `installed=` helper emits a source build twelve commits ahead
of the release and incorrectly expects that downgrade to pass.
