The new barrier precedes all entity, append, and checkpoint writes. It waits on

## P1: retain a durable legacy baseline before making its file disposable

`TrustStore::recover` adopts a v1 file at a nonzero epoch, but retains no separate
baseline. The first `update_at` replaces that file with a v2 projection through
`TrustPersister::write_batch` and unsynced `write_atomic`. The file now contains
both pre-epoch history and replayable post-epoch changes. Only the latter are
a disposable cache.

Recovery falls back to the epoch when the file is missing, unreadable, or ahead
of the chain. For an ahead/unreadable file, it first renames the whole file to
`.corrupt` (`core/src/storage/trust.rs`, `recover`). `ServerState::open` then
replays only from that epoch (`replay_trust_projection`). It rebuilds the
post-epoch suffix over a fresh entity, losing the baseline from served trust.

The author's comment already discloses the ahead-file legacy limitation. Its
scope is wider than a pre-barrier cache or a restored chain: **losing a migrated
cache file while retaining the entire chain has the same result**. A barrier
orders cache writes after chain durability; it does not make the overwritten
legacy baseline recoverable. The existing manifest check detects the missing
file but cannot restore that baseline.

Two test-only reproductions use the real sealed store and recovery code with
modeled chain positions:

1. Seed a durably written, sealed v1 entity with seven actions. Recover at chain
   length 10, establishing epoch 10. Apply row 10 and flush: count is eight.
2. Missing-file case: close, remove the migrated entity file, retain the epoch
   and checkpoint, recover at length 11, and replay retained row 10. Count is
   **one**, where preserving the baseline requires **eight**. No chain rollback
   or cache-ahead condition is involved.
3. Ahead-file case: additionally apply row 11 before closing. Recover against
   length 11, modeling a prefix that retains row 10 but loses row 11. The ahead
   file is quarantined. Replaying row 10 again produces **one**, rather than
   the correct **eight**.

Preserve a sealed, durable per-entity baseline before replacing a legacy file
with a disposable projection, and rebuild the suffix over that baseline.
Alternatively, migrate the baseline into durable chain evidence with a
crash-safe migration contract. When an existing baseline cannot be recovered,
do not serve a fresh entity as if reconstruction succeeded. This affects trust
scores and history, not merely the diagnostic action count.
