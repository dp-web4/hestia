## #1265: authorization no longer waits on the reported lock

The debug route now has its own `debug_gate`, outside `operator_gate`.
`OperatorSessionView` holds the principal and issuance time under a separate
lock; `SessionStore::open`, `close`, and `gc` maintain that view. Expiration is
also checked when resolving the bearer. The statistics handler and ordinary
authorization path require no state-lock acquisition.

The served-router regression holds the state lock in another task and checks
an authenticated report plus missing/wrong-bearer refusals. This exercises the
middleware path that the original handler-only argument missed.

Two scope limits remain explicit: the debug gate does not repeat the current
law's bootstrapped-operator check, and the development override schedules its
witness asynchronously. This closes the reported availability defect; it does
not establish stronger atomic authorization/witness guarantees for that override.

## #1266: checkpoint failure fixed; do not ship the intermediate head alone

`checkpoint_error_is_fatal` classifies SQLite IOERR, corruption, and
not-a-database errors as fatal. The checkpoint result now reaches `poison`,
which fails waiters, refuses further appends, and invokes the installed fatal
hook. The regression substitutes the main-file `xSync`, confirms it was called,
and checks poison plus append refusal after `SQLITE_IOERR_FSYNC`.

The earlier keyed-append replay and vault pre-save repairs remain present.
The higher-level replay/delivery repair is deliberately absent from this
exact head: it lives in #1268. The author has documented that dependency, and
the integrated code supplies it. **#1266 is not independently cleared for
merge/deployment without #1268.** A sequence that deploys the intermediate
#1266 or #1267 revision retains the reader/delivery defect.

## #1267: the documentation now matches the implementation

The publication and its shared mutable session directory are no longer claimed
to provide an atomic paired read. The module now states the two-read
interleaving, immutable existing identities, removal behavior, and treatment
of a session added after publication capture. It also states the stronger
capture/versioning requirement for future code that needs paired atomicity.

This addresses the requested narrowing of the claim. It does not add that
stronger guarantee. No new stage-2 blocker was established in this follow-up;
the intermediate branch retains the reader-barrier dependency above.

## #1268: admission, read snapshot, and dashboard repairs

Both ordinary `enqueue_member` and `enqueue_egress` now use `write_conn`, so
their chain barrier precedes row insertion. Operation-keyed admission and
updates of its replay/shadow record also use that barrier. A persisted replay
or deliverable row therefore cannot first appear before the witness it names
is durable through these paths. The remaining direct inbox connection reads
do not admit such rows; the documented liveness touch carries no chain fact.

`SqliteChainStore::observed` begins a read transaction and obtains
`MAX(chain_position)+1` in its first SELECT. Every later query on the guarded
connection uses that same snapshot, and the guard ends the transaction. Both
chain connections and aggregate reads use this mechanism. This closes the
gap between sampling a counter and executing the read. The flusher also
covers the requested snapshot frontier when it exceeds the handle's own
commit counter, avoiding an indefinitely pending read of another handle's row.

`fold_dashboard_snapshot` captures the length with the fold it actually
returns, including the second fold, and raises it to the read high-water
recorded by the projection/derivation reads. The worker waits before publishing.

These changes resolve the two P1s and the dashboard P2 from review 18933, and
supply the higher-level replay/delivery repair required by #1266.
