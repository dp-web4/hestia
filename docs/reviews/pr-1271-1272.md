## #1271: P1 — make charge application and its recovery identity atomic

`TrustPersister::write_batch` (`core/src/storage/trust.rs:396–417`) durably replaces
trust files before appending settlement records. This orders two effects; it does
not make them atomic. Two recovery failures are reproducible:

1. **Lost charge:** hold the trust persister, witness a deny, then witness a warn
   for the same member/action. The second chain row carries `charge_held_by` from
   the in-memory decision ledger. Fail the pending trust batch and reopen.
   `decision_witness::rehydrate` treats that chain field as proof of settlement,
   although no trust charge reached disk. Retrying the deny returns
   `charged=false`; action count remains 0.
2. **Double charge:** make only the settlement append fail (a directory at its
   destination). The trust file becomes durable, then the append fails and
   poisons the persister. Repair the destination and reopen. The original
   decision is found, but its settlement is absent, so retry applies the charge
   again: action count 0 → 1 on disk → 2 after retry, for one decision.

The second crash-window class existed in the former split-write design too;
this PR's ordering and fatal-restart rule do not establish its advertised
exactly-once recovery guarantee. The first becomes a process-level loss with
write-behind: a later chain row can outlive trust still held only in memory.
The rewritten failure tests stop before any trust file lands and therefore
exercise neither case.

Persist the application identity with the trust mutation (for example, in one
replayable transactional journal), then derive settlement from that durable
identity. Do not use `charge_held_by` alone as proof that asynchronous trust
persistence completed. Add recovery coverage for both sides of the commit gap.

## #1271: P1 — include observed trust in reader durability waits

`TrustStore::load` returns the new cached value immediately. Only `enqueue`
registers the trust frontier through `note_frontier`; a read does not.
`ServerState::on_release` registers only the chain frontier even inside
`durable_scope_observing`.

With the trust persister held, a cached read completes successfully with action
count 1 while a separately reopened store reads count 0. The same failure is
reproduced through `read_resource_body("hestia://society/trust/gemini")` wrapped
in the observing scope used by the MCP resource handler. It acknowledges the
updated count without waiting for the held write.

A writer waiting before its own reply cannot prevent another request from
acknowledging its unpersisted state. Track the trust sequence observed by reads
and wait for it, or serve readers from a durable snapshot. Cover both resource
and operator read surfaces.

## #1272: P1 — make rate-limit admission atomic before evaluating concurrently

`tool_query_policy` now calls `published.evaluate` outside the state lock
(`core/src/server/handler.rs:1552–1554`). The shared `Arc<RateLimiter>` preserves
one counter, but `PolicyEngine::evaluate` still calls `check` and `record`
separately (`core/src/policy/engine.rs:75–79`). Each takes and releases the
limiter mutex. Concurrent evaluations can both observe the last free slot,
both return allow, and then both increment it. The earlier handler lock
serialized those calls.

The reproduction clones one engine across 16 synchronized threads with an
enforced deny rule at `max_count=1`. On round 2, **two evaluations returned
allow**. No production code or scheduler hooks were modified. This reproduction
is scheduler-dependent; the source-level interleaving is the underlying issue.
The existing clone test checks pointer equality, not admission behavior.

Add a single check-and-record operation under one limiter lock and use it from
evaluation. Test concurrent admissions across live and published engine clones.

## Follow-up: #1272 rate-limit repair

Notice 19085 points to the author's repair at
`f001b4d0ecec3fb9979628e46bbf8df130fd0442`. The diff from the reviewed head
changes only the policy engine and rate limiter. `RateLimiter::admit` now holds
the windows mutex across pruning, checking the count, and recording an accepted
call. `PolicyEngine::evaluate` uses that operation, and live and published
engine clones retain their shared limiter. This closes the reported last-slot
check/record interleaving.

The new tests exercise 16 simultaneous callers for 200 rounds each: three
admissions on a limiter with capacity three, and one allowed evaluation across
alternating live/published clones with capacity one.

Independent validation on a clean checkout of that exact repair commit:

```sh
cargo test --manifest-path core/Cargo.toml -j2 --lib policy:: -- --nocapture
```

Result: **89 passed, 0 failed**, including both concurrent admission tests.
The reported #1272 rate-limit P1 is resolved on this commit.

This follow-up addresses only the #1272 rate-limit finding. The inherited
