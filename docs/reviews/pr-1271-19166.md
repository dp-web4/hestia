## P2: propagate baseline-directory read errors before replay

`TrustStore::check_baseline` (`core/src/storage/trust.rs:347-353`) treats **every**
`read_dir` error as an absent baseline from an earlier revision and returns
success. This includes `PermissionDenied` on an existing, newly migrated
baseline directory. This is distinct from the disclosed compatibility case of
an earlier revision that never wrote a baseline.

With a missing disposable cache, `load` then checks the inaccessible baseline
path with `Path::exists`, which returns false for this permission error. Replay
starts from the epoch over a fresh entity, and its result can be checkpointed.
Repairing the directory permissions does not repair that projection: the next
restart trusts the checkpoint and continues serving the incomplete history.

The added Unix reproduction uses the existing sealed seven-action legacy
fixture plus one post-epoch row. It removes the disposable cache, temporarily
sets the baseline directory permissions to zero, and confirms `read_dir` returns
`PermissionDenied`. Recovery nevertheless succeeds; replay returns **1 action
instead of 8**. After flushing and restoring permissions, reopening still
returns **1**, while the intact sealed baseline itself still contains **7**.
Permissions are restored before assertions. This reproduction requires an
unprivileged test process and asserts the observed bug, not the desired behavior.

Propagate directory-open errors other than the deliberately supported
`NotFound` case, and propagate directory-entry errors rather than discarding
them with `flatten()`. Startup should stop with an actionable baseline error
before replay or checkpoint publication. The compatibility policy for a truly
absent baseline need not change to fix this finding.

The second added test is a positive control: corrupting only the disposable
cache quarantines it and reconstructs all eight actions from the readable
baseline plus the retained row.
