## P2 — Do not treat every failed rename as a concurrent seed installation

Location: held patch lines 70–75, the new identity-seed installation block.

`mv -n "$seed_tmp" "$seed_dst" 2>/dev/null || true` suppresses every move failure.
The following test checks only whether the temporary file remains. It then deletes
that file and records `seed_state="present"`, without checking the destination.
A rename error therefore looks like a successful competing writer even when no
destination exists. The installer can publish a current manifest with no seed;
subsequent current-build cycles will not retry the missing installation.

Reproduced by executing the exact added seed block under `set -euo pipefail` in a
temporary fixture with an existing source seed and no destination, replacing only
`mv` with a shell function returning 1. Result:

```text
installer seed block rc=0
ok identity.seed.json (appeared during this install; left as-is)
manifest seeds: ... "state":"present"
DESTINATION MISSING
```

Require destination evidence before calling this a race won by another writer;
otherwise fail the installation before publishing the manifest. Keep the existing
never-overwrite rule. Pin both genuine concurrent creation and rename failure
without a destination.

## P2 — Preserve exact-tag candidates in the upgrade harness

Location: `tools/upgrade_path_test.py:185–189`, used at lines 901 and 968 and in
the manifest checks.

`core/build.rs` produces `git describe --tags --always --dirty`, which returns a
bare tag such as `v0.0.5` at a tagged commit. The new `names_commit` requires a hex
abbreviation, so both harness arms reject a correctly built tagged candidate with
`SetupError`. The previous upgrade arm compared the candidate's describe string
with the binary's string and accepted this case. Rebuilding as instructed by the
new error cannot change the result.

Reproduced in an isolated Git fixture with one clean commit tagged `v0.0.5`:
the actual producer command returned `v0.0.5`, the old equality check passed, and
`names_commit(described, full_candidate_sha)` returned `False`.

Resolve exact tags against the source repository and verify their commit, or keep
a verified exact-describe fallback. Apply the same rule to manifest validation.
This is a regression in candidate validation, separate from implementing a new
tag-based deployment mode.

## P2 — Check the seed beside hydrate's registered path

Location: `tools/upgrade_path_test.py:778–779`.

The new `seed_findings` unconditionally chooses the first installed file's path.
The held installer correctly prefers `hydrate.sh` when choosing the seed anchor.
Those paths may differ for existing registrations, which the installer derives
individually. The harness can therefore report failure with the correct seed in
place, or report success while hydrate's fallback has no seed.

Reproduced with a synthetic manifest whose first file is `gate/hooks/gate.py` and
whose hydrate entry is `hydrate/hooks/hydrate.sh`:

- Seed only at hydrate's fallback: harness reports `FAIL` beside the gate.
- Seed only beside the gate, hydrate's fallback absent: harness reports `ok`.

Select the hydrate entry before falling back to the first installed file, matching
the installer. Pin the two split-registration cases above.
