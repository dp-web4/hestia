## #1265: debug-route authorization still waits for the lock (P2)

This head is identical to the head previously reviewed. In
`core/src/server/http.rs`, `/api/debug/locks` is registered at line 1308 under
the `operator_gate` middleware at lines 1317–1320. That middleware acquires the
state lock at line 578; the development override also acquires it. The handler's
separate statistics mutex does not let a real authenticated request inspect a
holder while that holder keeps the state lock.

Preserve authorization while making its necessary inputs available independently
of the contested lock. Test the HTTP route through its middleware with the state
lock held. This finding is reconfirmed by source inspection, not a new HTTP
reproduction.

## #1266: partial repair of the previous durability findings

The `append_once` replay now registers the existing row with the durability
scope, and vault saves have a pre-save chain barrier. Those are real repairs.

Two previously reported P1 paths remain on this exact head:

* `Durability::checkpoint` (`core/src/storage/durability.rs:321–344`) still
  treats every checkpoint error as a retryable warning. The previous
  `SQLITE_IOERR_FSYNC` reproduction exercised SQLite's synchronization callback
  but did not poison the store. The error-handling branch is unchanged. Fatal
  synchronization failures must reach the same poison/fatal path as the custom
  flusher; routine checkpoint contention can remain retryable.
* Fixing chain-level `append_once` does not close every dependency on an existing
  witness. `tool_member_notify` can return `op.response_json` without an append
  when the shadow witness is already present (handler.rs around 5134).
  `tool_member_inbox` returns or drains inbox rows (around 7907–7955) without
  joining their witness frontier. This head lacks the later durable-read/inbox
  barriers. A read-only `durable_scope` still completes with no target. The
  earlier witness-before-reply/delivery finding therefore remains for these
  paths. Include the durable-read repairs before treating this branch as
  independently mergeable.

No new checkpoint fault injection or inbox-delivery reproduction was run in this
wake. The fresh replay and vault-barrier tests run on #1272's combined head;
they are not represented as an exact-head #1266 test run.

## #1267: unchanged stage-2 assessment

The changes since the previous reviewed `1f460fd4` consist of the #1266 replay
and vault-barrier repair. `published.rs` and `state_lock.rs` are byte-identical
to their previously reviewed versions. No new blocking defect was established
in the stage-2-only change; the stack remains blocked by #1266.

The existing consistency caveat also remains: a captured publication retains a
shared mutable `Arc<SessionDirectory>`, and `published()` releases the slot read
lock before `resolve()` locks that directory. Publishing the directory and
policy under one write lock does not make those two later reads atomic. Current
production session identities are stable, so this is a limit on the general
claim, not a newly established end-to-end exploit. A paired identity/policy
mutation test would be needed before relying on the stronger guarantee.
