## P1: a surviving checkpoint cannot certify independently unsynced cache files

`TrustPersister::write_batch` (`core/src/storage/trust.rs:522`) replaces each
entity file, then writes `projection.json`. `write_atomic` does neither file
nor directory fsync. Writing the checkpoint last orders syscalls; it does not
establish a durable dependency across the files. After a system crash an entity
may be absent or stale while the newer checkpoint survives. Independently lost
cache files have the same recovery problem.

`ServerState::open` (`core/src/server/state.rs:627`) unconditionally starts at
`through + 1`. It neither verifies that the checkpoint's entity state survived
nor repairs missing entities from their earlier rows. An entity's own `through`
only suppresses duplicates for rows replay actually visits; it cannot recover
rows skipped by the global start position.

Reproduction `review_19153_surviving_checkpoint_skips_a_lost_entity`:

1. Witness a deny inside `durable_scope`; await successful chain durability.
2. Flush the cache; the execution grain has action count 1.
3. Close, remove only that entity's cache file, and retain the checkpoint and
   the entire durable chain. This constructs the recovery image; it does not
   claim to have induced a physical power failure.
4. Reopen: count is 0. Retry the same decision: `charged=false`, count still 0.

Make startup reconstruct any missing/stale cache state, or make a checkpoint
usable only with a verifiably complete, crash-consistent cache snapshot. An
unsynced global watermark alone cannot be authority for skipping chain facts.

## P1: a partial first batch is misclassified as legacy state

`ServerState::open` (`core/src/server/state.rs:629`) treats any entity file with
no readable projection record as a legacy cache and adopts it at the current
chain head. `has_entity_files` checks filenames, not their v1/v2 representation.

On a fresh projection store, a process can die after one entity's rename in the
first batch and before another entity's rename or the final checkpoint write.
That is a v2 partial projection, not a complete legacy baseline. Startup moves
both the replay start and the epoch to the chain tail, permanently skipping the
unwritten entity's charge. This case needs no power-loss reordering.

Reproduction `review_19153_partial_first_batch_is_mistaken_for_legacy`:

1. Hold the first cache batch and durably witness one deny each for two members.
2. Materialize the files, then construct the partial-batch image: keep one v2
   entity; remove the other entity and `projection.json`. Keep the chain intact.
3. Reopen: the surviving member has count 1, the other count 0, and the originally
   fresh projection epoch has been advanced above zero.

Distinguish a genuine legacy baseline from an interrupted v2 projection. Recover
the latter from the appropriate original epoch; do not adopt it at the tail.
The migration marker/baseline must itself have an explicit crash-safe contract.
