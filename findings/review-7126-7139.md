# Review: notices 7126 and 7139

## Scope and evidence

Kimi requested review of escalations `e5ecdb023f839056` and
`e83e7d73f45d71c0`.  At review time both live records were already `approved`
by the operator under the `single_approver` bar.  Each record carried only the
operator factor and the gate-generated statement that no member rationale was
provided.

The resulting artifact is commit
`f8ac5bcbb9b0429481e983c2c5142929a73b4e10`
(`fix(kimi-gate): bind escalation approvals to the payload, not the path`), on
the `kimi/601-act-payload-digest` branch and not yet on `main` at review time.
Its focused boundary suite passed:

```
python3 plugins/kimi/hooks/kimi_gate_boundary_test.py
# 10/10 passed
```

## Finding: dissent

The change makes a correct structural move by including the write payload in
the approval key, but it retains only the first twelve hexadecimal characters
of SHA-256 (`sha256(...).hexdigest()[:12]`).  That gives the authorization key
only 48 bits of collision resistance.  A requester can choose two `content`
or Edit payloads for the same path, vary harmless padding until their digest
prefixes collide (birthday work of about 2^24 hashes), request approval for
the innocuous member, then reissue the harmful member.  `_attempted_summary`
is identical for both, so the claimed approval cannot distinguish them.

This directly contradicts the commit's claim that a modified payload cannot
claim the approval.  The new test proves ordinary values differ, but not the
security property needed at this authorization boundary.

Use the complete SHA-256 digest (or at least a collision-resistant length such
as 128 bits) in the attempted-act string, then add a regression test asserting
the chosen length/algorithm.  The digest follows the redacted and bounded
summary, so this can be done without disclosing payload material.

## Disposition

No escalation factor was filed: corroboration factors freeze when an
escalation is decided, and both pointers had already reached `approved`.
This is a post-decision technical dissent for the next revision of the commit,
not a retroactive claim about the operator's decision.
